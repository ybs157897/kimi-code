## 1. 产品定义

### 1.1 原始需求

构建一个购物平台的后端系统，支撑多用户在线购物场景，涵盖从用户注册登录、商品浏览选购、下单支付到物流配送的完整交易链路。当前为分析阶段，无需编码实现，产出 PRD 供后续架构师进行系统设计。

### 1.2 产品目标

1. **支撑完整的交易闭环** — 提供从用户注册、商品管理、购物车、订单、支付到物流配送的端到端能力，确保交易链路畅通、数据一致。
2. **保障业务可扩展性** — 系统模块解耦，支持多卖家入驻、促销活动、评价体系等扩展功能，降低新增业务模块的集成成本。
3. **保障数据安全与订单准确性** — 在用户身份鉴权、库存扣减、支付对账等关键环节提供可靠保障，防止超卖、数据不一致等问题。

### 1.3 用户角色

| 角色 | 描述 |
|------|------|
| **买家 (Buyer)** | 在平台注册、浏览商品、加入购物车、下单并支付，使用物流和评价等功能 |
| **卖家 (Seller)** | 在平台开店、管理商品信息、处理订单发货、回复评价 |
| **管理员 (Admin)** | 管理平台运营，审核商品、管理用户、配置营销活动、查看数据报表 |

## 3. 核心功能模块描述

### 3.1 用户服务 (User Service)

负责用户的注册、登录、身份鉴权与基本信息管理。支持买家和卖家两种角色，提供 OAuth 或 JWT 的登录方式。需要提供用户等级、收货地址管理等附加能力。

### 3.2 商品服务 (Product Service)

管理商品基本信息（标题、描述、图片）、类目树、品牌、属性模板与 SKU（库存量单位）体系。支持商品上下架操作，提供商品详情查询接口和类目导航能力。

### 3.3 购物车服务 (Cart Service)

管理买家购物车中的商品项。支持添加商品、修改数量、移除商品、清空购物车。需处理未登录（本地缓存）与登录后（服务端同步）的场景，支持购物车合并。

### 3.4 订单服务 (Order Service)

订单是全链路的中心环节。覆盖订单创建（从购物车生成 OR 直接购买）、订单状态流转（待支付 → 已支付 → 已发货 → 已完成 → 已取消）、订单详情查询、取消与退款申请。需保证订单号唯一、状态变更可追溯。

### 3.5 支付服务 (Payment Service)

对接外部支付网关（支付宝/微信等），生成支付单、处理支付回调、同步支付状态。需与订单服务协同完成支付成功后的订单状态推进，以及支付失败/退款的处理。

### 3.6 库存服务 (Inventory Service) — P1

管理商品 SKU 的可售库存。在用户下单时锁定库存、支付成功后扣减库存、取消订单时回滚库存。需解决高并发下的超卖问题（如乐观锁或分布式锁）。

### 3.7 物流服务 (Logistics Service) — P1

卖家发货后录入物流单号与承运商，买家可查询物流轨迹。支持多包裹发货、配送方式切换。

### 3.8 促销服务 (Promotion Service) — P1

管理优惠券模板、发放与核销，以及满减、限时折扣、秒杀等营销活动规则。促销活动涉及价格计算，需与订单服务和购物车服务协同。

### 3.9 评价服务 (Review Service) — P1

交易完成后买家可对商品进行评分和文字评价，可上传图片。卖家可回复评价。评价数据用于商品展示和推荐系统。

### 3.10 搜索服务 (Search Service) — P2

基于 Elasticsearch 等引擎建立商品索引，提供关键词全文检索、多维筛选、排序和分页能力。

### 3.11 推荐服务 (Recommendation Service) — P2

基于用户画像、浏览历史、购买记录和商品关联规则，为买家提供个性化商品推荐。

### 3.12 通知服务 (Notification Service) — P2

通过站内消息、短信、邮件或推送通道，向用户发送订单状态变更、物流更新、促销活动等信息。

### 3.13 后台管理 (Admin Console) — P2

为平台运营人员提供统一管理界面，包括用户管理、商品审核、订单查询、数据统计报表等能力。

## 4. 用户故事

### P0 用户故事

## 5. UI 设计稿参考（文字描述）

> 后端系统的 UI 主要指 **管理后台** 和 **买家前端交互流程**。以下描述供前端/全栈同学参考。

### 5.1 买家端核心流程

1. **首页 / 商品列表页**
   - 顶部搜索栏 + 类目导航
   - 商品卡片网格：商品缩略图、标题、价格、销量
   - 点击商品进入详情页

2. **商品详情页**
   - 商品图片轮播、标题、价格、规格选择（SKU）
   - "加入购物车" 和 "立即购买" 按钮
   - 用户评价摘要

3. **购物车页**
   - 商品列表（勾选、数量调整、删除）
   - 价格汇总区域（商品金额 + 运费 + 优惠减免）
   - "去结算" 按钮 → 进入订单确认页

4. **订单确认/结算页**
   - 收货地址选择 / 新增
   - 商品清单（不可再修改数量）
   - 支付方式选择、优惠券选择
   - 订单金额汇总
   - "提交订单" 按钮 → 跳转支付

5. **支付页 / 支付结果页**
   - 支付二维码 / 唤起收银台
   - 支付成功 → 订单详情页
   - 支付失败 → 重试 / 更换支付方式

6. **订单列表 / 订单详情页**
   - 按状态（待付款 / 待发货 / 待收货 / 已完成）分类筛选
   - 订单卡片：商品信息、实付金额、状态标签
   - 点击进入详情：物流信息、操作按钮（取消订单、确认收货、评价）

### 5.2 卖家端核心流程

1. **商品管理页面** — 商品列表、新增商品表单（标题/图片/类目/SKU/价格/库存）
2. **订单管理页面** — 待发货订单列表 → 发货操作（填入物流单号）
3. **评价管理页面** — 查看买家评价 → 回复

### 5.3 管理后台核心页面

1. **数据看板** — 今日订单数、GMV、新增用户、热销商品排行
2. **用户管理** — 用户列表、封禁/解封、角色分配
3. **商品审核** — 待审核商品列表 → 通过/驳回
4. **营销管理** — 优惠券创建、活动配置

## 6. 待确认问题

以下问题需要在进入架构设计前与需求方进一步确认：

1. **支付方案** — 需要对接哪些第三方支付渠道（支付宝、微信支付、银联等）？是否支持跨境支付？平台是否有支付牌照，资金是平台代收代付还是直接由卖家收款？
2. **多店铺模式** — 平台是自营模式（平台统一卖货），还是多卖家入驻（B2C/C2C）？如果是多卖家模式，卖家的入驻审核流程和佣金结算方式是什么？
3. **库存与超卖容忍度** — 秒杀/高并发场景下，系统对超卖的容忍程度如何？是严格的"不允许超卖"（需要分布式锁），还是允许一定程度超卖后用售后流程处理？这直接影响库存服务的架构选型。
4. **外部系统对接范围** — 是否需要对接已有的 ERP/WMS（仓储管理系统）进行库存同步？是否需要与第三方物流平台（如菜鸟、顺丰 API）对接自动获取物流轨迹？
5. **国际化需求** — 平台是否计划支持多语言、多币种、多地区？这会影响商品属性结构、价格体系和订单系统的基础设计。
